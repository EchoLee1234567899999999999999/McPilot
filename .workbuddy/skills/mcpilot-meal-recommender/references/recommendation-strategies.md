# 三种推荐策略（Phase 2 实现 / Phase 3 质量优化）

三种策略共享**硬约束**，区别在**打分侧重**。选择规则：用户说"省钱/划算/便宜"→ `budget`；说"高蛋白/增肌/营养"→ `nutrition`；说"帮我搭配一份/均衡一点"或未指明 → `balanced`（默认三者都算，便于对比）。

> 实现位置：`src/mcpilot/recommender.py`（打分）、`src/mcpilot/combos.py`（组合生成）。

---

## 共享前提

### 硬约束（不满足直接淘汰）
- **在售**：所有餐品必须来自 `query-meals` 的真实返回；指定商品不在售直接报错。
- **"是一餐"**：候选**必须含一份主食**（`main` 主餐或 `set` 套餐）；单份饮料/甜点不作候选。
- **份额**：组合总份数 ≥ 用餐人数（`people`）。
- **预算上限**（若给出）：**真实实付**（`calculate-price`）≤ 预算；超出的候选被剔除。
- **营养目标**（若给出 `protein_g_min` / `energy_kcal_max` / `fat_g_max`）：
  只保留**能确认达标**的组合；营养未知的组合**无法确认 → 剔除**（不臆造达标）。
- **忌口**：商品**名 / 标签 / 套餐组成**命中忌口关键词（如"辣"）即淘汰。
- **不满足需求的方案绝不以"最优推荐"名义输出**：若全部候选被硬约束剔除，返回空方案 + 明确告警。

### 价格口径（重要）
- 菜单展示价（元）**仅用于筛选/排序**；对外"实付"必须来自 `calculate-price`（分→元）。
- 全程使用**整数分**参与计算；**不缓存价格**（每轮重新查询，不以缓存冒充实时）。

### 候选组合生成（受限枚举）
- 商品按角色分类：`set` / `main` / `side` / `drink` / `dessert`（启发式，仅用于生成）。
- 每个角色取**最便宜的 K 个**，并额外并入三类高价值商品，避免被价格截断：
  1. **营养可靠且蛋白最高**的商品；2. **券适用**的商品；3. **口味偏好命中**的商品。
- 组合模式：套餐（单件即完整一餐）、main+side+drink / main+side / main+drink / main+dessert、
  main（兜底）；`max_distinct_items`（默认 3）与 `max_candidates`（默认 2000）双重封顶。
- 去重：按 `(编码 × 数量)` 排序签名去重；**同一购物车不重复试算**。

### MCP 调用预算（性能约束）
- 固定 3 次：`query-meals`、`list-nutrition-foods`、`query-store-coupons` 各 1 次。
- `query-meal-detail`：**仅**对进入试算的候选做规范名/套餐组成解析，**有缓存**，
  次数 ≤ `max_resolve`（默认 10）。
- `calculate-price` 仅对**轮转选出的少量候选**试算，次数 ≤ `max_verify`（默认 12）。
- 筛选阶段只用营养表与展示价，**不额外消耗 MCP 调用**。

---

## 策略 A：省钱型（budget）——实付最低（但必须"是一餐"）

**打分（越高越好）**：`0.85 × 实付占优 + 0.10 × 节省率 + 0.05 × 分量充足度`

- `实付占优 = 1 − 实付 ÷ 候选最大实付`（权重最高 → 优先实付更低）
- `节省率 = 优惠 ÷ 原价`（真实来自 `calculate-price`）
- `分量充足度 = min(1, 件数 ÷ (2 × 人数))`（客观件数，非主观饱腹感）
- 排序键先判"含主食且满足人数"，再比实付——**不会**因为某杯饮料最便宜就把它当一餐。

**输出**：实付最低的可行组合，标注是否用券。

**示例理由**：`实付 ¥13.90（原价 ¥13.90，优惠 -¥0.00），在预算 ¥30.00 内，为候选方案中实付最低`
+ `满足用餐需求：精选超值随心配×1，共 1 件（含主食）`

---

## 策略 B：高蛋白型（nutrition）——预算内蛋白最高

**打分（越高越好）**：`0.70 × 蛋白质 + 0.15 × 热量偏好 + 0.15 × 预算利用`

- **仅当组合营养数据可靠**（每件商品都能可靠匹配营养表：精确/归一化/别名/规范名/套餐组成）
  才返回分数；否则**不进入定量排名**（`score_nutrition` 返回 `None`）。
- **初始排名 = 蛋白质最高**（并列时实付更低者优先），在预算内把可靠计算的蛋白质做到最大。
- `热量偏好`：用户给出热量目标时按接近度；否则偏好较低热量。

**输出**：营养可靠的候选中蛋白质最高的组合，同时展示热量与蛋白质。

**示例理由**：`蛋白质合计 30.0 g、热量 578 kcal（为可可靠匹配营养的候选中蛋白质最高）`

---

## 策略 C：综合型（balanced）——性价比取舍

**打分**：对**可用**维度加权平均（缺失维度不参与、不补 0）：

| 维度 | 权重 | 说明 |
|------|------|------|
| 蛋白质性价比 | 0.35 | `蛋白质(g) ÷ 实付(元)`，按候选最大值归一化；**仅可靠营养参与** |
| 分量充足度 | 0.15 | 客观件数 ÷ (2 × 人数) |
| 口味命中度 | 0.15 | 命中偏好关键词数 ÷ 偏好关键词数（无偏好时不参与） |
| 预算余量 | 0.20 | `1 − 实付 ÷ 预算`，温和的成本偏好 |
| 数据完整度 | 0.15 | 组合是否全部商品营养可靠（未知 → 0，不臆造） |

> 不使用任何主观"饱腹感/口感"评分；所有维度都能追溯到 MCP 返回的真实数据。
> 用户给出口味偏好时，偏好命中的商品会被强制纳入候选池，避免"只取最便宜"把偏好商品挡在门外。

**示例理由**：`综合评分 0.73：蛋白质性价比 0.88｜分量充足度 1.00｜预算余量 0.07｜数据完整度 1.00`

---

## 营养匹配分层（Phase 3）

高蛋白型与综合型都依赖"营养可靠匹配"。菜单名是 **UI 简名**，营养表是**规范全名**，因此采用分层匹配：

| 层级 | 说明 | 附加调用 |
|------|------|----------|
| `exact` | 名称字面完全相同 | 无 |
| `normalized` | 仅全/半角、空白、括号、引号、™® 等编码差异 | 无 |
| `alias` | **人工审核**别名表（每条含依据） | 无 |
| `canonical` | 用 `query-meal-detail` 的**规范全名**再匹配 | ≤ `max_resolve` |
| `composition` | 套餐按详情**默认组成**逐项匹配后加权合计 | ≤ `max_resolve` |

**明确拒绝**（会导致错误匹配）：套餐名"包含"单品名；去「套餐」后缀；口味变体；规格不明按经验补默认规格。
任何一层都匹配不到 → 标"营养缺失"，**不猜测、不当 0**。

---

## 策略差异保证

三种策略分别取各自的最优；若某个策略的最优与更靠前策略重复，则取**下一个不重复且同样真实**的方案，
并在理由中注明"为与其它策略呈现不同方案"。真实可行组合不足时，允许返回少于三种，
**绝不为了凑数编造商品**（会给出"真实可行组合不足"的说明）。

## 兜底规则

| 情况 | 处理 |
|------|------|
| 无门店券 | 正常出结果，注明"当前门店/订单类型下无可用门店券" |
| 券不适用（适用商品不在本店菜单） | 正常出结果，如实说明"券无法使用（按真实编码比对判定，不套用）" |
| 券过期 / 未生效 | 排除该券并说明 |
| 预算不足 | 返回空方案 + 提示，并用 `calculate-price` 试算**真实最低实付**作为调整建议 |
| 营养缺失 | 标注"营养未知"，不进营养排名；综合型按数据完整度扣分 |
| 目标不可达 | 返回空方案 + 明确告警，不返回未经 MCP 验证的价格 |
| 接口超时 / 报错 | 只读幂等 → 限次重试（指数退避）；仍失败则汇总原因、如实降级 |
