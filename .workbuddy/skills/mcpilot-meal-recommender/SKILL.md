# McPilot · 麦门决策局

## Overview

把"今天吃什么、怎么点最划算"变成一个**可信、透明、可复现**的答案。本技能编排麦当劳官方 MCP 的**只读**工具，按用户给定的**预算 / 营养目标 / 口味偏好 / 可用优惠券**，输出带实付价格与用券建议的餐品组合推荐。

**硬性前提**：所有价格、营养、优惠券、门店数据**必须来自 MCP 实时返回**，禁止编造或写死；本技能**只做只读调用**，不进入任何下单/领券流程。

## When to Use

在以下情形触发本技能：

- 用户请你帮忙**搭配**一份麦当劳（如"帮我点一份麦当劳""两个人吃怎么搭"）。
- 用户给出**预算**（"30 元以内""别超过 40"）。
- 用户给出**营养诉求**（"热量别太高""想吃高蛋白""少油/低钠"）。
- 用户给出**口味偏好**（"想吃炸鸡""要辣的""加份薯条"）。
- 用户问"**有哪些优惠券能用**""**这些一共多少钱**"。
- 用户需要在**到店自取**或**得来速**场景下做点餐决策。

## When Not to Use

- 用户要**下单/支付/取消订单** → 本技能**不做**（仅可提示"确认后可下单"，但当前阶段不调用下单工具）。
- 用户要**领券 / 抽奖 / 积分兑换** → 本技能**不做**。
- 用户要**外送（麦乐送）/ 企业团餐** → 当前阶段不覆盖（见 roadmap）。
- 用户仅做**纯知识问答**（如"麦当劳是哪年创立的"）→ 无需调用本技能。

## Required Inputs

在开始推荐前，尽量收集齐以下信息；缺失项可**先默认、后确认**，不要空转：

| 输入 | 是否必需 | 缺省策略 |
|------|----------|----------|
| 场景：到店自取 / 得来速 | 必需 | 默认**到店自取**（`beType=1`） |
| 门店：城市 / 位置关键词 / 收藏 | 必需 | 先查收藏，无则按位置搜索 |
| 预算上限 | 推荐 | 无则不限，仅给最优搭配 |
| 用餐人数 | 可选 | 默认 1（决定最少份数） |
| 营养目标（蛋白下限 / 热量上限） | 可选 | 无则不做营养硬约束 |
| 口味偏好（想吃/忌口） | 可选 | 无则不做口味加权 |
| 指定必含商品 | 可选 | 无 |
| 是否用券 | 可选 | 默认**尽量用券** |

## MCP Tools

本技能仅使用以下**只读**工具（调用契约详见 `references/mcp-tools.md`）：

| 工具 | 作用 |
|------|------|
| `query-nearby-stores` | 查询可点餐门店 |
| `query-meals` | 查询门店餐品 / 套餐列表 |
| `query-meal-detail` | 查询餐品详情与可特调项 |
| `list-nutrition-foods` | 获取营养数据 |
| `query-store-coupons` | 查询门店可用优惠券 |
| `calculate-price` | 价格试算（含优惠） |

> **禁用**：`create-order`、`auto-bind-coupons`、`draw-lottery`、`mall-create-order`、`party-order-create`、`cancel-order`、积分/地址写入等一切写操作。

## Workflow（调用顺序）

按以下顺序执行，**价格试算必须最后**：

1. **确认场景与参数**
   - 明确到店自取（`beType=1`）还是得来速（`beType=5`）。
   - 参数规则：自取 → `orderType=1` 且**不传** `beCode`；得来速 → `orderType=1` 且**必传** `beCode`。
   - `reservationDate` 仅预约场景传，格式 `yyyy-MM-dd HH:mm`。

2. **门店查询** — `query-nearby-stores`
   - 先尝试收藏（`searchType=1`）；无结果回退按位置（`searchType=2`，需 `city` + `keyword`）。
   - 展示门店并**引导用户选择**；记住 `storeCode`（得来速连同 `beCode`）。

3. **菜单查询** — `query-meals`（必要时 `query-meal-detail`）
   - 拉取门店在售餐品/套餐及其 `code`。
   - 详情里 `supportModify=true` 的项标注【可特调】；**不主动展开**特调选项。

4. **营养匹配** — `list-nutrition-foods`（必要时 `query-meal-detail`，**有界**）
   - 将用户营养诉求解析为硬约束（上限/下限）与偏好。
   - **分层匹配（严格）**，依次尝试，任一层命中即采用，并记录依据：
     1. `exact` 名称字面相同；
     2. `normalized` 仅全/半角、空白、括号、引号、™® 等**编码差异**；
     3. `alias` **人工审核**的别名表（每条含依据）；
     4. `canonical` 用 `query-meal-detail` 返回的**规范全名**再匹配（菜单简名→全名）；
     5. `composition` 套餐：按详情返回的**默认组成**逐项匹配后加权合计。
   - **明确拒绝**（会导致错误匹配，一律不做）：套餐名"包含"单品名（如「巨无霸四件套」⊉「巨无霸」）；
     去掉「套餐」后缀再匹配（「麦香鸡套餐」≠「麦香鸡」）；口味变体（「那么大鸡排（椒盐风味）」≠「那么大鸡排」）；
     规格不明时按经验补默认规格（「薯条」≠「中薯条」，除非详情明确）。
   - 组合营养按数量**加权求和**；有一项无法可靠匹配即标"营养未知"并**排除在营养定量排名外**，
     **绝不用部分合计冒充整体、绝不把未知当 0**。
   - `query-meal-detail` 解析**受 `max_resolve` 限制（默认 10）**，同一名称只解析一次。

5. **优惠券查询** — `query-store-coupons`
   - 取"该门店 + 该订单类型"可用券，做门槛、适用商品与**时效**（生效/过期/未生效）匹配。
   - 券的三种来源：**门店可用券**（本项目真实调用）／**账户已有券**（`query-my-coupons`，账号级，**不调用**）／
     **可领取券**（`auto-bind-coupons`，写操作，**不调用**）。后两者只做说明，绝不伪造。
   - 券是否适用**只以 `products[].productCode` 与组合商品编码比对为准**；不适用的券绝不套用。

6. **组合生成与打分** — 见 `references/recommendation-strategies.md`
   - 先按**展示价 + 营养表**生成并粗筛候选（不额外消耗 MCP 调用），
     再把少量候选交给 `calculate-price` 做真实试算。
   - **候选必须"是一餐"**：至少含一份**主食**（主餐或套餐），并满足人数与指定商品；不含主食的组合不作候选。
   - **用户偏好/必含商品必须进入候选池**：口味偏好命中的商品、用券适用商品、蛋白最高商品都会强制纳入，
     避免被"只取最便宜"的价格截断挡在候选之外。
   - 三种策略（与需求一一对应）：
     - `budget` 省钱型：**真实实付最低**（在"是一餐"的前提下）；若最终只有一件散件主食，
       **必须标注为「经济单品方案」**，不得宣称是营养完整的一餐（套餐单件除外）。
     - `nutrition` 高蛋白型：**双口径**——默认按**蛋白质密度（g/100kcal）**为主排序
       （避免"用热量换蛋白"被误判为更优），并给出蛋白/价格参考；只有当用户**明确要求**
       最大化绝对蛋白质（说"蛋白最多""蛋白质最高"等，或把蛋白下限设到 ≥30g）时，
       才切换为**总量优先**。两种口径都**只统计营养可靠匹配的组合**。
     - `balanced` 综合型：蛋白质性价比 / **甜点搭配度** / 分量 / 口味 / 预算余量 /
       数据完整度的**可解释加权**。
   - **不禁止甜品、饮料**：是否加入由**真实营养数据**（甜品热量占比）、用户偏好与评分规则共同决定，
     并在推荐理由中说明依据；用户明确点名时优先。无甜品**不扣分**（该维度不参与）。
   - **硬约束严格执行**：忌口（名称 / 标签 / 套餐组成）、指定商品、营养上限/下限都是硬门槛，
     不满足者直接剔除；**不满足用户需求的方案绝不作为"最优推荐"输出**。
   - 若某策略的最优与更靠前的策略重复，取**下一个同样真实的方案**并说明
     （统一标注「三策略去重说明：…（跳过 N 个已有组合）」）；
     真实可行组合不足时允许少于三种，**绝不编造商品凑数**。

7. **价格试算** — `calculate-price`
   - 对每个候选组合（含券）试算，**金额单位为分，展示时除以 100 转元**。
   - 实付**必须**来自该工具返回；菜单展示价只用于筛选，绝不作为最终价。
   - **不缓存价格**：每一轮推荐都重新查询，绝不以缓存价冒充实时价。
   - 试算次数受 `max_verify` 限制（默认 12），详情解析受 `max_resolve` 限制（默认 10），避免过量请求。

8. **输出推荐**（格式见下）

## 输出格式

对 Top-N 组合逐条给出：

```
【推荐 N｜策略：省钱优先】
组合：巨无霸 ×1 + 中薯条 ×1 + 中可乐 ×1
营养：约 XXX kcal（蛋白质 XX g，蛋白密度 X.X g/100kcal）   ← 来自 list-nutrition-foods（不可靠则标注"营养未知"）
用券：满 30 减 8（券名）            ← 来自 query-store-coupons
原价：¥XX.00  优惠：-¥X.00  实付：¥XX.00   ← 来自 calculate-price
理由：1) ... 2) ... 3) ...
数据来源：麦当劳 MCP 实时返回（门店 <storeCode>）｜查询时间 <datetime>
```

- 金额一律以**元**展示（内部以分为单位计算），结构化输出同时提供「分」与「元」。
- **价格为主视觉**，附关键指标（蛋白质 / 热量 / 蛋白密度）；营养明细与评分细节**可折叠**，
  但不得省略"数据范围与试算时间"说明。
- 营养合计**仅当组合内每件商品都精确匹配**时才给出；否则只标注"营养未知"，不用部分合计冒充整体。
- 无可用券、营养缺失、预算不足等情况如实标注，不臆造。

## Safety & Compliance

- **只读**：绝不调用任何写操作工具（下单、领券、抽奖、积分、地址写入）。
- **真实数据**：所有业务数值来自 MCP 返回，禁止编造或写死。
- **凭据零落盘**：不得输出、记录、写入 Token、`Authorization` 请求头或账号信息。
- **降级不造假**：接口异常时如实告知并降级，绝不返回编造结果。

## Error Handling

| 情况 | 处理 |
|------|------|
| 无搜索门店结果 | 回退按位置搜索；仍无则引导更换城市/关键词 |
| 门店无在售餐品 | 直接报错"未返回任何在售餐品"，不编造菜单 |
| 无门店券 | 注明"当前门店/订单类型下无可用门店券"，继续完成推荐 |
| 券过期 / 未生效 | 排除该券并说明；不套用失效券 |
| 券适用商品不在本店菜单 | 如实说明"券适用商品不在本店在售菜单，本次无法使用"，**不套用** |
| 预算不足 | 用 `calculate-price` 试算**真实最低实付**，报告差距与调整建议（不编造） |
| 营养信息缺失 | 标注"营养未知"，**不进营养定量排名**，综合型按数据完整度扣分 |
| 营养目标不可达 | 返回空方案 + 明确告警（营养未知无法确认达标即剔除，不臆造达标） |
| 商品下架 / 菜单变化 | 指定商品不在售 → 直接报错；价格试算失败 → 剔除该候选并记录 |
| 接口报错 / 超时 | 只读幂等 → **限次重试（指数退避）**；仍失败则汇总原因、如实降级，不返回编造数据 |

## Implementation Layer（本仓库提供）

本仓库在 `src/mcpilot/` 提供**确定性逻辑层**，负责解析、匹配与推荐（避免反复手写）：

- `mcp_client.py` — 只读工具客户端（含参数规则、白名单守卫、**超时与限次重试**）。
- `menu.py` — 菜单解析 + `query-meal-detail` 的**规范全名 / 套餐默认组成**解析。
- `nutrition.py` — 营养分层匹配（归一化 / 别名 / 规范名 / 套餐组成）+ **覆盖率报告**。
- `resolve.py` — 营养按需增强器（有缓存、**有调用上限**）。
- `coupon.py` — 券解析、**时效判定**、来源分类与适用性匹配。
- `pricing.py` — 价格试算解析（分→元）。
- `combos.py` — 候选组合生成与约束（角色分类、**含主食硬要求**、预算/口味/人数/指定商品过滤、规模封顶）。
- `recommender.py` — **三种推荐策略**、打分、推荐理由与结构化输出（含 CLI）。
- `pipeline.py` — 端到端最小链路（门店 → 菜单 → 营养 → 券 → 价格），可直接运行。
- `scripts/phase3_report.py` — Phase 3 验收脚本（覆盖率 / 券 / 三预算耗时）。

两种等效的调用方式（详见 `docs/02-architecture.md` 第 9 节）：

- **由 Skill 调度 MCP**：智能体调用 `mcp__mcd-mcp__*` 工具，把返回交给上述逻辑层解析/推荐。
- **Python 直连 MCP**：
  - 最小链路：`python -m mcpilot.pipeline --store <storeCode> --be-type 1 --items 1100:1`
  - **直接出推荐**：`python -m mcpilot.recommender --store <storeCode> --be-type 1 --budget 30`
    （可加 `--people 2`、`--like 炸鸡`、`--dislike 辣`、`--include 1100`、`--max-verify 12`、`--max-resolve 10`、`--json`）
  - **验收报告**：`PYTHONPATH=src python scripts/phase3_report.py --store <storeCode> --be-type 1`

> 无论哪种方式，业务数值都必须以 MCP 实时返回为准；不得使用任何写死的价格/营养/券。
