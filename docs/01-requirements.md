# 功能需求文档（Functional Requirements）

> 项目：McPilot · 麦门决策局 ｜ 文档版本：v0.2（Phase 2）
> 关联文档：[02-architecture.md](02-architecture.md)、[03-mcp-tools.md](03-mcp-tools.md)

---

## 1. 背景与目标

用户在麦当劳点餐时同时面对多个约束：**预算有限、想控制热量/营养、有口味偏好、手上还有若干优惠券**。人工逐项比对门店、菜单、营养表和券，成本高且容易算错。

本项目的目标：构建一个 **AI Skill**，把上述多约束决策自动化——**调用麦当劳官方 MCP 获取真实数据**，输出"吃什么 + 怎么搭最合适 + 实付多少 + 用了哪张券"的可执行建议。

### 1.1 设计原则

1. **真实数据**：价格、营养、优惠券、门店一律来自 MCP 返回，禁止编造或写死。
2. **只读安全**：当前阶段只调用只读工具，绝不触发下单、领券等写操作。
3. **可解释**：每条推荐必须给出理由与关键数据支撑。
4. **降级可用**：任一数据源缺失时不报错崩溃，而是降级并如实说明。
5. **凭据零落盘**：不得将 Token、请求头、账号信息写入任何文件或日志。

### 1.2 术语约定

| 术语 | 含义 |
|------|------|
| `storeCode` | 门店编码 |
| `beCode` | 业务编码，与 `storeCode` 配对；得来速/外送/团餐场景必传 |
| `beType` | 业务场景：`1` 到店自取、`5` 得来速、`2` 麦乐送、`6` 企业团餐 |
| `orderType` | 订单类型：`1` 到店（含自取+得来速）、`2` 外送（含麦乐送+团餐） |
| 组合 / Combo | 一个或多个餐品、可含数量与特制选项的集合 |
| 实付 | 经优惠券抵扣后的应付金额 |

### 1.3 关键参数传递规则（统一约定）

| 用户场景 | `beType` | `orderType` | `beCode` |
|----------|----------|-------------|----------|
| 到店自取 | 1 | 1 | **不传**（传了会报错） |
| 得来速 DT | 5 | 1 | **必传**（来自 `query-nearby-stores`） |
| 麦乐送 | 2 | 2 | 必传（来自 `delivery-query-stores`） |
| 企业团餐 | 6 | 2 | 必传（来自 `delivery-query-stores`） |

> **Phase 0 范围**：仅覆盖 **到店自取（beType=1）** 与 **得来速（beType=5）** 两种到店场景；外送/团餐列入 roadmap。

## 2. 使用者旅程（主流程）

```
用户：帮我推荐一份 30 元以内、热量别太高的到店午餐
  │
  ├─(1) 确认场景：到店自取 or 得来速？
  ├─(2) 门店查询  → 用户选定门店
  ├─(3) 菜单查询  → 门店在售餐品/套餐
  ├─(4) 营养匹配  → 按营养目标筛选候选
  ├─(5) 优惠券查询 → 门店+订单类型可用券
  ├─(6) 组合生成  → 按策略组合候选
  ├─(7) 价格试算  → 计算实付
  └─(8) 输出推荐  → Top-N 组合 + 理由 + 实付 + 券
```

## 3. 功能需求明细

### FR-1 门店查询

**目标**：定位用户可点餐的门店。

**输入**：`searchType`（1 收藏 / 2 按位置）、`beType`（1 自取 / 5 得来速）、`city`、`keyword`（`searchType=2` 时必填）。

**处理**：
- 优先尝试收藏门店（`searchType=1`）；无结果则回退按位置搜索（`searchType=2`）。
- 得来速（`beType=5`）需完整保留 `beCode`；自取（`beType=1`）门店无 `beCode`。
- 若返回 `reservation=true`，完整展示 `reservationTimeOptions`，`today=true` 标注"(今天)"。

**输出**：门店列表，含 `storeCode`（及得来速的 `beCode`）、门店名、地址/距离、可选预约时段。

**验收标准**：
- AC-1.1 用户未指定门店时，必须先查询并引导选择，不得自行臆造门店。
- AC-1.2 得来速场景后续所有调用都必须携带对应 `beCode`。
- AC-1.3 无搜索结果时，提示更换关键词/城市，不报错中断。

**MCP**：`query-nearby-stores`

---

### FR-2 菜单查询

**目标**：获取门店在售餐品与套餐组成。

**输入**：`storeCode`、`orderType`、`beType`、（得来速）`beCode`、（可选）`reservationDate`。查详情时另需餐品 `code`。

**处理**：
- `query-meals` 拉取餐品/套餐列表，记录每个餐品的 `code`、名称、价格相关字段、`支持随单购` 标记等。
- `query-meal-detail` 获取需细化考察餐品的组成：
  - `data.supportModify=true` → 名称后标注【可特调】；`choice.supportModify=true` → 该 choice 标注【可特调】。
  - **不主动展开**特调选项，仅当用户询问时展示。
  - 展示后总结默认选中的搭配（`isDefault=1` 的 choices）。

**输出**：结构化菜单（餐品/套餐 + 组成 + 是否可特调）。

**验收标准**：
- AC-2.1 所有候选餐品都必须来自 `query-meals` 真实返回，禁止使用记忆中的菜单。
- AC-2.2 展示价格时不得写死，一律以 MCP 返回为准。
- AC-2.3 特调信息不主动打扰用户，响应式提供。

**MCP**：`query-meals`、`query-meal-detail`

---

### FR-3 营养匹配

**目标**：按用户营养目标筛选/排序候选餐品。

**输入**：用户营养诉求（如"热量 ≤ 600 kcal""高蛋白""少油""低钠"）；`list-nutrition-foods` 返回的营养表（能量、蛋白质、脂肪、碳水化合物、钠、钙等）。

**处理**：
- 将用户自然语言诉求解析为**约束**（硬约束：上/下限）与**偏好**（软目标，参与打分）。
- 以餐品名称/编码匹配营养表条目，计算组合的合计营养。
- 营养数据缺失的餐品：**不臆造**，标记为"营养未知"，在营养策略中降权或排除并说明。

**输出**：候选组合的营养合计 + 达标情况（达标 / 超出 / 未知）。

**验收标准**：
- AC-3.1 营养数值必须来自 `list-nutrition-foods`，缺失即标注缺失。
- AC-3.2 组合营养合计需给出计算口径（按数量加权求和）。
- AC-3.3 无法匹配的餐品不得被默认判定为"低热量"。

**MCP**：`list-nutrition-foods`

---

### FR-4 优惠券查询

**目标**：找出"该门店 + 该订单类型"下用户可用的优惠券。

**输入**：`storeCode`、`orderType`、`beType`、（得来速）`beCode`、（可选）`reservationDate`。

**处理**：
- 获取可用券列表（含 `couponId` / `couponCode`、门槛、优惠形式、适用商品等）。
- 将券与候选组合进行**适用性匹配**：门槛是否满足、适用商品是否命中、是否互斥。
- 输出"每张券 → 可用于哪些组合 / 能省多少"。

**输出**：可用券清单 + 与组合的匹配关系。

**验收标准**：
- AC-4.1 券信息必须来自 `query-store-coupons`，不得虚构券。
- AC-4.2 无券可用时，明确告知"当前门店无可用优惠券"，并继续完成推荐（不阻断）。
- AC-4.3 不得调用 `auto-bind-coupons` 等任何领券类写操作。

**MCP**：`query-store-coupons`

---

### FR-5 价格试算

**目标**：对候选组合计算含优惠的实付金额。

**输入**：`storeCode`、`orderType`、`beType`、（得来速）`beCode`、`items[]`（`productCode` + `quantity` + 可选 `couponId`/`couponCode` + 可选 `modification`）、（可选）`needTableware`、（可选）`reservationDate`。

**处理**：
- 对每个候选组合调用 `calculate-price`，得到含优惠的价格明细。
- **单位换算**：返回价格单位为**分**，展示时除以 100 转为**元**（保留 2 位）。
- 支持"带券/不带券"两次试算，用于量化券的价值。

**输出**：原价、优惠金额、实付、券使用情况。

**验收标准**：
- AC-5.1 实付金额必须来自 `calculate-price`，禁止本地估算或写死。
- AC-5.2 展示金额一律为"元"，内部计算以"分"为整数避免浮点误差。
- AC-5.3 试算失败（如商品下架）时，剔除该组合并说明，不中断整体推荐。

**MCP**：`calculate-price`

---

### FR-6 推荐引擎与三种策略

**目标**：在满足硬约束的前提下，按策略生成 Top-N 推荐组合。

**输入**：预算上限、用餐人数、营养目标、口味偏好/忌口、指定必含商品、可用券、菜单、价格。

**通用约束（所有策略共享）**：
- **硬约束**：真实实付 ≤ 预算、门店在售、场景一致（到店/得来速）、
  营养目标达标（营养未知组合无法确认达标 → 剔除）、忌口商品不进候选、
  组合总份数 ≥ 人数（不允许"明显不满足用餐需求"的极简组合被判为最优）。
- **打分**：先过滤硬约束，再按策略打分排序；金额以**整数分**计算。

#### 策略 A：省钱型（Budget）
- 目标：**真实实付最低**。
- 打分：`0.85×实付占优 + 0.10×节省率 + 0.05×分量充足度`
  （实付占优权重最高；分量充足度只统计客观件数）。
- 输出：预算内实付最低的可行组合，并标注是否用券。

#### 策略 B：高蛋白型（Nutrition）
- 目标：预算内**蛋白质最高**。
- 打分：`0.70×蛋白质 + 0.15×热量偏好 + 0.15×预算利用`。
- **仅当组合内每件商品都能在营养表中精确匹配时**才参与定量排名；
  营养未知的商品既不猜测、也不当作 0。
- 输出：营养可靠的候选中蛋白质最高的组合，同时展示热量与蛋白质。

#### 策略 C：综合型（Balanced）
- 目标：**性价比取舍**，兼顾预算、口味、蛋白质与数据可靠性。
- 打分（对**可用**维度加权）：蛋白质性价比 0.35 / 分量充足度 0.15 /
  口味命中度 0.15 / 预算余量 0.20 / 数据完整度 0.20。
- **不使用任何主观"饱腹感/口感"指标**；营养缺失时相关维度不参与（不补 0），
  且"数据完整度"归零。
- 输出：可解释评分最高的组合，并列出各维度得分。

> 三策略应尽量给出**不同**的方案；真实可行组合不足时允许少于三种，绝不编造商品凑数。

**验收标准**：
- AC-6.1 每个推荐必须可追溯到具体 MCP 数据（餐品、价格、券、营养）。
- AC-6.2 硬约束不满足的组合不得进入推荐结果（含营养目标与忌口）。
- AC-6.3 每条推荐输出："组合清单 + 原价/优惠/实付 + 使用券 + 推荐理由（1~3 条）+ 数据缺失提示"。
- AC-6.4 结果须标注数据来源与查询时间（来自 MCP 返回的 `datetime`）。
- AC-6.5 推荐结果可序列化为 JSON（供后续前端消费）。

**MCP**：组合调用 FR-1 ~ FR-5 的工具

## 4. 非功能需求

| 类别 | 要求 |
|------|------|
| 真实性 | 所有业务数值仅来源于 MCP 实时返回，无本地写死/编造数据 |
| 安全 | 只调用只读工具；凭据零落盘；日志脱敏 |
| 可解释 | 每条推荐附理由与关键数据 |
| 健壮性 | 外部接口异常时降级并如实说明，不伪造结果 |
| 可移植 | 核心逻辑零/极少第三方依赖，便于评审复现 |
| 可测试 | 服务层与策略层可注入式接口，便于 mock 与单测 |
| 合规 | 可直接公开上传 GitHub，不含任何敏感信息 |

## 5. 输出契约（推荐结果字段）

| 字段 | 说明 |
|------|------|
| `items[]` | 餐品列表（`code`、名称、数量、角色、逐行金额、单项营养） |
| `strategy` | 使用的策略（budget / nutrition / balanced） |
| `label` | 策略中文名 |
| `price` | 原价 / 优惠 / 实付（同时给出「分」与「元」） |
| `coupon` / `coupon_note` | 实际使用/试算的券及其说明（不含账号相关字段） |
| `nutrition` / `nutrition_missing` / `nutrition_complete` | 营养合计与缺失口径 |
| `score` | 该策略下的得分 |
| `reasons` | 推荐理由（1~3 条，可追溯真实数据） |
| `notes` | 数据缺失 / 降级提示 |
| `data_source` / `queried_at` | 数据来源与查询时间 |

> 顶层为 `RecommendationPlan`：`store_code`、`be_type`、`be_code`、`request`、
> `recommendations[]`、`warnings[]`、`suggestions[]`、`stats`（含各工具真实调用次数）、
> `data_source`、`queried_at`。

## 6. 边界与异常（详见测试计划）

- 无可用优惠券 / 券不适用 → 正常返回，注明"门店券的适用商品未命中组合"，`discount = 0`。
- 预算不足 → 用 `calculate-price` 试算**真实最低实付**，给出差距与调整建议。
- 营养信息缺失 → 标注"营养未知"，不进入营养定量排名；综合型按数据完整度扣分，不臆造。
- 营养目标不可达 → 返回空方案 + 明确告警，不返回未经 MCP 验证的价格。
- 商品下架 / 菜单变化 → 指定商品不在售直接报错；试算失败的候选剔除并记录。
- 接口报错/超时 → 如实告知失败原因，不返回编造数据。
- 门店不存在/无结果 → 引导重新选择。
