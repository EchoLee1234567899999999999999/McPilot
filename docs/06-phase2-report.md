## 2. 三种策略（已实现）

| 策略 | 目标 | 打分（越高越好） |
|------|------|------------------|
| `budget` 省钱型 | 真实**实付最低** | `0.85×实付占优 + 0.10×节省率 + 0.05×分量充足度` |
| `nutrition` 高蛋白型 | 预算内**蛋白质最高** | `0.70×蛋白质 + 0.15×热量偏好 + 0.15×预算利用`；**仅营养可靠组合参与** |
| `balanced` 综合型 | **性价比**取舍 | 蛋白质性价比 0.35 / 分量 0.15 / 口味 0.15 / 预算余量 0.20 / 数据完整度 0.20 |

- 综合型**不使用任何主观"饱腹感/口感"指标**，所有维度都可追溯到 MCP 真实数据。
- 策略间若最优重复，取"下一个同样真实、评分次优"的方案，并在理由中说明；
  真实可行组合不足时允许少于三种，**绝不编造商品凑数**。

## 3. 关键实现要点

### 3.1 两段式：粗筛（免费）→ 真实试算（受限）
1. 固定 3 次只读查询：`query-meals`、`list-nutrition-foods`、`query-store-coupons`；
2. 用**展示价 + 营养表**生成并粗筛候选（零 MCP 调用）；
3. 轮转选出少量候选（≤ `max_verify`，默认 12）交给 `calculate-price`；
4. 最终**实付一律取自 `calculate-price`**，展示价只用于筛选。

### 3.2 候选不遗漏高蛋白 / 可优惠项
候选池默认只取"最便宜 K 个"，会把高蛋白主餐（如安格斯、巨无霸）与券适用商品挡在外面。
因此额外把**"营养可靠且蛋白最高"**与**"券适用商品"**并入候选池。

### 3.3 硬约束
- 真实实付 ≤ 预算（超出的候选剔除并计数）；
- 营养目标（`protein_g_min` / `energy_kcal_max` / `fat_g_max`）只保留**能确认达标**的组合，
  营养未知者无法确认 → 剔除（不臆造达标）；
- 忌口关键词命中的商品**不进入候选池**；
- 组合总份数 ≥ 用餐人数（避免"明显不满足用餐需求"的极简组合被判为最优）。

### 3.4 数据缺失绝不臆造
- 营养表按**餐品名精确匹配**；未命中即"营养未知"，**不计入合计、不当 0**；
- 组合营养合计**仅当全部商品可靠匹配**时才给出（否则只报缺失，不用部分合计冒充整体）；
- 未使用券时 `discount = 0` 并如实说明原因。

## 4. 真实运行结果（门店 3330324，到店自取，预算 ¥30）

```
候选 448 个（预算内 74）｜试算 12 次｜MCP 调用 {'query-meals':1,'list-nutrition-foods':1,'query-store-coupons':1,'calculate-price':12}

【省钱优先】¥13.90 —— 精选超值随心配×1
  理由：实付 ¥13.90（原价 ¥13.90，优惠 -¥0.00），在预算 ¥30.00 内，为候选方案中实付最低

【高蛋白优先】¥30.00 —— 双层深海鳕鱼堡×1 + 圆筒冰淇淋×1
  营养：578 kcal｜蛋白 30.0 g（候选最高）
  理由：营养数据完整，可参与定量排名

【综合推荐】¥28.00 —— 双层吉士汉堡×1 + 圆筒冰淇淋×1
  营养：522 kcal｜蛋白 29.0 g
  理由：综合评分 0.73：蛋白质性价比 0.88｜分量充足度 1.00｜预算余量 0.07｜数据完整度 1.00

⚠ 门店券的适用商品未命中任何候选组合，本次均未使用优惠券。
```

**为什么这样选**：
- 省钱型取全局最低实付（¥13.90 的 1+1 随心配，本身即完整一餐）；
- 高蛋白型在预算内最大化蛋白质：¥25 鳕鱼堡（28 g）+ ¥5 圆筒冰淇淋（2 g）= 30 g，
  在预算 ¥30 处取到该预算下的最高蛋白质；
- 综合型按**性价比**取舍：¥23 双层吉士汉堡（27 g）搭配圆筒后性价比与分量俱佳，
  且不与高蛋白型重复。

## 6. 完成 / 未完成 / 暂无法验证

### ✅ 已完成
- 三种可解释、真实可计算的策略；多商品组合生成与硬约束；
- 真实 `calculate-price` 验证（实付、优惠、逐行小计一致性）；
- 券适用性判定与"券不适用"如实标注；结构化 JSON 输出（含查询时间与数据来源）；
- 预算不足时给出**真实最低实付**与调整建议；
- 调用次数上限（3 次只读查询 + ≤12 次试算）。

### ⏳ 未完成
- 得来速（`beType=5`）真实 `beCode` 端到端未跑通（承接 Phase 1 遗留）；
- 外送 / 团餐场景未覆盖；
- 重试与超时策略仍为"单次调用 + 明确报错"（Phase 3）。

### ⚠️ 暂无法验证
- **真实门店券的实际减免**：当前门店（3330324）两张券的适用商品编码（`9900014239`、`9900016370`）
  均不在该店菜单中，因此"券不适用"是**真实结论**；"券适用并真实减免"这条代码路径
  仅在高置信度的**合成夹具**下验证过，尚缺一次真实成功样本。
- **营养型排名覆盖面**：营养表仅约 20/125 个菜单商品可精确匹配（名称口径差异所致），
  这是数据现状而非实现缺陷；坚持"不确定就标注缺失、绝不猜测"的原则。
- **真实环境价格波动**：示例输出为采集当时快照，价格随活动变化。

Phase 2 的三种推荐策略已在**真实 MCP 数据**上跑通，结果可解释、金额可追溯、异常不编造。
