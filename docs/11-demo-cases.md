# 三种推荐策略 — 真实演示案例

> 以下全部数据来自**麦当劳官方 MCP 实时返回**（2026-10-09 实测，测试门店 #3330324，
> 到店自取 `beType=1`）。试算金额来自 `calculate-price`（单位分，展示转元），
> 营养来自 `list-nutrition-foods` 分层匹配，券适用性按真实商品编码判定。
> 复现命令见文末。

## 场景设定

| 参数 | 值 |
|---|---|
| 预算 | ¥50 |
| 人数 | 1 |
| 门店 | 深圳 #3330324（菜单 127 件） |
| 数据规模 | 候选 448 个 → 预算内 408 个 → 真实试算 12 个 |

---

## 策略 1：省钱优先（budget）

**结果：精选超值随心配 ×1 — 实付 ¥13.90**（评分 0.621）

- **为什么**：在"组合必须含主食"的硬约束下，这是候选中**真实实付最低**的方案。
- **用券**：未使用 —— 门店两张券（「麦旋风任选」「薯薯任选」）的适用商品编码
  不在该组合中，且适用商品已不在本店菜单（按真实编码比对判定，**不套用**）。
- **营养**：如实标注"营养缺失"——该套餐名在营养表各层均无法可靠匹配，
  **不猜测、不按 0 计、不给部分合计**。
- **诚实标注**：该方案为**套餐单件**（套餐本身即完整一餐），不触发"经济单品"警示；
  若最便宜的方案是散件单主食（如仅一个汉堡），会明确标注为**「经济单品方案」**，
  不宣称是营养完整的一餐。

## 策略 2：高蛋白优先（nutrition）

**结果：培根安格斯厚牛堡 ×1 — 实付 ¥34.50｜707 kcal｜蛋白质 34 g**（评分 0.758）

- **为什么**：**蛋白质密度（g/100kcal）最高的可靠匹配组合**。
  - 默认口径 = 密度优先（4.8 g/100kcal，0.99 g/元）——避免"用热量换蛋白"的方案
    （如多塞一个冰淇淋凑总量）被误判为更优。
  - 若用户**明确要求**「蛋白最多」，切换为总量口径：此前同店实测中
    「培根堡+圆筒冰淇淋（800kcal/36g）」会重新胜出。
- **蛋白质效率**（写进推荐理由）：4.8 g/100kcal ｜ 0.99 g/元。
- **诚实性**：只统计营养**全部可靠匹配**的组合；营养未知的商品不进定量排名、不按 0 计。

## 策略 3：综合推荐（balanced）

**结果：芝士安格斯厚牛堡 ×1 + 圆筒冰淇淋 ×1 — 实付 ¥36.50｜789 kcal｜蛋白质 34 g**（评分 0.826）

- **评分构成**（可解释加权）：蛋白质性价比 0.95｜**甜点搭配度 1.00**｜分量充足度 1.00｜
  预算余量 0.27｜数据完整度 1.00。
- **为什么不禁止甜品**：冰淇淋 93 kcal 仅占组合热量 12%（阈值内），
  用户未设热量上限、口味无冲突 → 按真实营养数据判断为"值得加入"，
  并在理由中写明依据。**反之**若甜品热量占比 ≥60% 会被大幅降权（0.4），无甜品**不扣分**。
- 与高蛋白策略的差异：不为单一指标牺牲体验，展示"多指标平衡"的选择。

## 三策略去重与诚实性

- 若某策略最优组合与前一策略重复，会**跳过并说明**
  （「三策略去重说明：…（跳过 N 个已有组合）」），不会把同一份组合改个名再端上来。
- 真实可行组合不足三种时**如实输出更少**，绝不编造商品凑数。
- 所有方案共享硬约束：真实实付 ≤ 预算、含主食、份数 ≥ 人数、忌口过滤、
  营养目标达标（未知的按"无法确认达标"处理）。

## 复现命令

```bash

# 2. CLI 直接出推荐（Python 直连 MCP）
PYTHONPATH=src python -m mcpilot.recommender --store 3330324 --be-type 1 --budget 50 --json

# 3. 或启动 Web 界面（Python 标准库，零构建）
python scripts/run_web.py     # 打开 http://127.0.0.1:8765/
```
