## Phase 3 —— 匹配优化与健壮性 ✅ 已完成（2026-10-09）

**结果**：营养分层匹配、券时效/适用性验证、推荐质量约束、有界重试与降级全部落地；
离线单元测试累计 **164** 条、真实集成 **14** 条全部通过。详见 [07-phase3-report.md](07-phase3-report.md)。

**本轮完成**：

1. **营养匹配**：`exact → normalized → alias → canonical → composition` 分层；
   覆盖率由纯精确匹配 **20/125 (16.0%)** 提升至静态 **24/125 (19.2%)**、叠加按需解析 **27/125 (21.6%)**；
   未命中一律标注"营养缺失"，**不猜测、不按 0 计**。
2. **券验证**：区分门店券 / 账户券 / 可领取券来源；增加时效（生效/过期/未生效）与适用性判定；
   真实门店 `3330324` 的两张券适用商品均不在本店菜单中 → **如实判定"不可用"**，无编造减免。
3. **推荐质量**：省钱型必须含主食（不得只取最便宜单品）；营养型仅在可靠匹配集内取最高蛋白；
   综合型与营养型差异化评分；忌口 / 指定商品 / 热量上限均为**硬约束**。
4. **健壮性**：传输类错误（超时/5xx/429）**有界重试 + 指数退避**；4xx 直接报错不重试；
   候选去重避免对相同购物车重复试算；`calculate-price` ≤ `max_verify`、`query-meal-detail` ≤ `max_resolve`。
5. **性能实测**：门店 `3330324` 三档预算耗时 ≈ 8.6~9.5 s，MCP 调用有界（详见测试计划 5.2）。

**本轮未完成 / 无法验证**：

1. 得来速（`beType=5`）仍缺真实 `beCode` 端到端验证（承接 Phase 1 遗留）。
2. **真实环境下的"用券成功产生减免"仍缺一次成功样本**：真实门店券适用商品不在本店菜单，
   该代码路径仅在高置信度合成夹具（明确标注 SYNTHETIC）下验证。**绝不伪造该结果**。
3. 营养覆盖率受**数据现状**限制（营养表用规范全名、菜单用简名，且部分商品无营养收录），
   剩余未匹配项如实保留为"营养缺失"。
4. 账户券（`query-my-coupons`）与可领取券（`auto-bind-coupons`）按约束**不调用**，故未验证。

## Phase 4 —— 产品界面与交互设计 ✅

**交付**（详见 [08-phase4-report.md](08-phase4-report.md)）：

- **Web 界面**：`src/mcpilot/web/`（Python 标准库 HTTP 后端 + 原生 HTML/CSS/JS 前端，零构建）。
  - 首页（预算/人数/口味/营养/真实门店选择 + ¥20/30/50 快捷键）
  - 查询状态页（SSE 真实进度事件驱动，非假进度）
  - 推荐结果页（三策略、官方图片、真实试算价、营养缺失标注、券说明、理由）
  - 可分享决策卡（像素风 Canvas 卡片，导出 PNG）
- **架构**：浏览器 → 127.0.0.1 后端 → `recommender.recommend` → 真实 MCP；
  Token 仅在服务端，前端零凭据；只读原则不变（写操作在客户端白名单处被拒）。
- **测试**：+20 条 Web API 离线测试、+3 条真实 Web 端到端；四态（加载/失败/超时/无数据）验证。
- **Skill 与 Web 为两个交付物**，共享 `src/mcpilot` 同一份核心推荐规则。

## Phase 4.3 —— 推荐结果质量与产品说明优化 ✅ 已完成（2026-10-09）

**交付**（详见 [10-phase43-report.md](10-phase43-report.md)）：

- **高蛋白双口径**：默认按**蛋白质密度（g/100kcal）**为主排序（0.50 密度 + 0.20 总量
  + 0.15 热量 + 0.15 预算利用）；仅当用户**明确要求**最大化绝对蛋白质时切为**总量优先**
  （0.70 总量 + 0.15 热量 + 0.15 预算利用）。判定函数 `wants_max_protein`。
- **新增辅助指标**：`protein_per_100kcal()`、`protein_per_yuan()`（非法输入返回 `None`）。
- **甜品/饮料不禁止**：综合型新增 `_treat_fit`（用户点名→1.0；热量占比 ≤25%→1.0，≥60%→0.4，
  中间线性；**无甜品→不参与**），由真实营养数据决定是否值得加入，理由中给出说明。
- **经济单品诚实标注**：`_is_bare_single_staple`（非套餐 + 1 件 + 数量 1 + 含主食）命中时，
  明确标注「经济单品方案」，**不宣称**营养完整一餐。
- **去重说明统一**：「三策略去重说明：…（跳过 N 个已有组合）」，三策略评分解释口径一致。
- **结果页信息层级**：价格主视觉 + 3 格指标（蛋白质/热量/蛋白密度）+ 官方图片；
  营养明细与评分/数据说明**默认折叠**；顶部保留**数据范围与试算时间**说明。
- **测试**：新增 `tests/unit/test_recommender_protein_efficiency.py`（24 条）；
  离线单元 **233 条（+1 skipped）**，真实集成 **21 条**。
- **真实复验**：`scripts/phase43_probe.py` 对门店 3330324 的 50 元场景做优化前后对比（见报告第 4 节）。

## 明确不做（Phase 4.3 重申）

- 不新增 MCP 写操作；不改变已验证的工具调用方式与参数规则。
- 不因"高蛋白"就禁掉甜品/饮料；不因"省钱"就把单件主食包装成完整一餐。
- 营养未知**不按 0 计**，不猜测、不用部分合计冒充整体。
